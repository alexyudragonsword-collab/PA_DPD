# 工程约束与陷阱

本文件是 `AGENTS.md` 硬约束一节的完整版。收录的都是**已经付过代价**的
条目——每条尽量写清"当时怎么表现的"和"为什么这么定",以免下次被同一个
坑用不同面貌绊倒。

## 当前结论

### 环境:工作区会静默回滚

容器可能在会话中途被回收,工作区随之退回旧提交,而 `git status` 看起来
完全正常。表现为文件"消失"、刚写的内容不见、`git log` 对不上。

- 处置:`git fetch origin <branch> && git reset --hard origin/<branch>`。
- 已推送的工作从未真正丢失;**未推送的会丢**,所以阶段性成果尽早提交。
- 单次会话中触发过 8 次;有两次发生在"写文件的过程中",导致新内容落在了
  旧树上——所以恢复后要核对关键文件的行数/标志性段落,而不是只看 `git log`。

### 测试:两处不能删的死锁修复

测试套件曾整体死锁,根因是三层叠加的,逐层剥出来的:

1. libgomp 屏障死锁 → `tests/conftest.py` 钉 `OMP_NUM_THREADS=1`;
2. 导入顺序问题 → 同文件里 pandas 预导入;
3. **真正的根因**:Qt widget 的析构函数被 GC 调度到 streamlit 的
   ScriptRunner 线程上执行,在 `QWindow::close → flushWindowSystemEvents`
   处永久阻塞,且持有 GIL,整个 pytest 进程挂死。

`tests/test_gui_qt.py` 的 fixture 因此显式做 `deleteLater()` +
`processEvents()` + `gc.collect()` 拆除。**新增 Qt 测试沿用这套 fixture,
不要自己造。**

### 数值:`np.allclose` 的默认 `atol`

检查时间列是否均匀采样时用了 `np.allclose(dt, dt[0], rtol=1e-6)`——
默认 `atol=1e-8` **秒**,在 100 MHz 以上比采样周期还大,于是抖动的导出被
静默放行,采样率取自它第一个(任意的)步长。写成 `atol=0.0`。

同类风险:任何对"物理量的小绝对值"用 allclose 的地方,都要显式给 atol。

### 校准:首采冻结类量对电平次序敏感

`ThermalReferencePA` 的耗散功率参考、`LoopbackChannel(rx_im3_freeze=True)`
的 κ 都在**第一次调用**冻结。踩到两次:

- 用回退到 0.1 倍的标定采集打头,κ 被冻高约两个量级;
- 用恒包络探针(功率 2.25)标定后再采突发波形(功率 ~0.55),热状态动态
  被压掉 4 倍,状态样条收益从 +10.5 dB 缩水成 +1.8 dB。

规则:标定采集必须在**标称工作电平**先做;表征探针与建模采集各用新建的
DUT 实例。这条对真实台架的采集顺序同样成立。

### 评估:状态模型的冷启动约定

单采集切分成训练/验证后,验证尾段**带着前段的热历史**,而模型的状态递推
从块首因果重算。必须"全信号预测、尾段打分";只对尾段预测等于假设了一个
它并不具备的冷启动,+10 dB 的收益会缩水成 +1。

### CI:矩阵与 test-full 的依赖集不同

快车道矩阵装 torch 但**不装 onnx**;`test-full` 装全套。一个 ONNX 测试
因此在开发机长期通过、云端长期红。写测试不要假设可选依赖存在,该
`pytest.importorskip` 就写上。

配额故障还会**掩盖真实失败**:仓库私有期 runner 未分配,所有 job 在 2 秒
内失败(`runner_id=0`),连续十几次提交都没有真实 CI 信号——转公开后一次
性暴露了两个陈年缺陷。看到"秒级失败 + runner_id=0"就知道不是代码问题。

### 建模:线性参数模型必须用 LS 闭式解

MP/GMP/DDR 这类**对系数线性**的模型一律用最小二乘闭式解,不要改成 SGD
迭代。同一个 GMP 用 SGD 训出来的 ACLR 比闭式解差 9 dB 以上,双重实证过。
只有真正非线性的参数(神经网络、样条结点位置)才需要迭代优化。

### GUI:Qt 侧的线程约定

- 耗时操作走 `FnWorker`,**在 GUI 线程上先把控件值快照成普通 Python 值**
  再传进闭包——worker 线程里访问 `QWidget` 不安全;
- 服务层函数放 `gui_core/services.py`(纯 Python,不 import 任何 GUI),
  两个 GUI 各接一次,不在页面里写算法。

### 文档:性能数字要三处同步

改动性能数字必须同时更新 `README.md`、`docs/05_performance_summary.md`、
`manual/zh|en`——三处曾各说各的。`tests/test_docs_site.py` 会检查 README
提到的每个 Phase 在 `docs/03_roadmap.md` 里存在(路线图曾落后两个阶段)。
改手册跑 `pytest tests/test_manual.py`;改 mkdocs 配置或 API 页跑
`pytest tests/test_docs_site.py`。

### 双前端验证:桌面全绿不代表 Android 可用

`gui_core/services.py` 是**三个前端共用的契约**(streamlit `gui/`、
PySide6 `gui_qt/`、Android `padpd_mobile/` + Kotlin)。桌面测试套件跑的是
Python 那一半;Android 那一半是 Kotlin,**本地没有 Android SDK,只在 CI 里
编译**。所以"测试全过"这句话在这个项目里天然只覆盖一半。

改到下面任何一处,两边都要验:

| 改动位置 | 为什么影响两边 |
|---|---|
| `gui_core/services.py` | 三个前端同一份契约 |
| `gui_core/i18n.py` | Python 的 `tr()` 与 Kotlin 的查表用同一张表 |
| `padpd_mobile/` | 桌面测试能覆盖(`tests/test_mobile_*.py`),但页面装配的效果只有设备端看得见 |
| `android/` | 只有 CI 能编译 |

**两边各自的"验过"标准:**

- **Qt/桌面**:`QT_QPA_PLATFORM=offscreen python -m pytest tests/ -m "not slow" -q`
  全绿,并如实报数字。
- **Android**:推上分支,读 Android workflow 的**两个** job 结论——
  「Build arm64 release」(编译 + JVM 单测 + 图表金图)与
  「Instrumented tests on emulator」(设备端 37 条)。**两个都绿才算验过。**

三条实际踩过的教训:

1. **只看构建绿不够**。设备 job 独立失败过多次(合并语义树、滚动视口、
   缺 import),而构建 job 是绿的。
2. **"绿"也可能是空的**。图表金图那步连续两轮退出码 0、产出 28 张空白图。
   现在有 `check-android-preview-renders.py` 逐个读预览结果。凡"某步骤成功"
   要能追到一个**计数或数值**,不能只看颜色。
3. **不要从产物反推步骤成功**。曾因"APK artifact 在"推断金图那步过了,
   实际是那个上传步骤带 `always()`。**读步骤结论,不读副作用。**

改 Kotlin 时还有一条:编译器在 4 分钟外,**选不可能出错的写法**,不选需要
写对的写法(用 `bounds.right - bounds.left` 而不是 `DpRect.width` 扩展属性)。
本会话在同一个文件上因此栽了三次。

### Android:一类反复出现的错觉——"存在"不等于"到得了"

Android 前端(`android/`,Kotlin UI + Chaquopy 嵌入 Python)踩过的坑,完整
记录在 `android/README.md`,那里有每条的报错原文与排查过程。这里只留索引,
因为它们有一个共同形状,而这个形状在别处也会出现:

- **Compose 语义树**:节点被 compose 出来了 ≠ 测试找得到它。三种变体——
  `clickable` 合并子节点 testTag、节点在横向滚动视口外、节点在纵向滚动
  视口外——症状都是"测试说没有,截图里明明有"。
- **Kotlin 块注释会嵌套**(Java 的不会):KDoc 里一个 `/*` 吃掉文件其余部分,
  报错却指向三个无辜文件。守卫在 `tests/test_mobile_pages.py`。
  该守卫后来又**误报**过一次(MIME 通配符里含注释结束符),处置是修守卫、
  跳过字符串字面量,**不是改被守的代码去迁就它**。
- **共享控件不能自带滚动**:控件不知道自己会被嵌进什么,横向滚动套横向滚动
  会以"infinity maximum width"抛异常。滚动由调用方负责。
- **testTag 不能用翻译后的 label 拼**:切语言就全变,设备测试随之失效。
  label 给人看,tag 是标识符。同 `gui_core/i18n.py` 的中文串硬约束一样,
  Kotlin 侧的可翻译串**必须是单个字面量**——Python 的 AST 折叠相邻字面量,
  Kotlin 的 `+` 不会。
- **SAF 给的是授权,不是路径**:`content://` 是可撤销的 provider 授权,
  背后文档可能没有任何文件系统路径。趁授权有效把字节拷出来是它的用法,
  不是绕过。provider 自选的显示名可能带 `/`,拼到目录上会写到别处去。
- **torch 在 Android 上没有轮子**:5 个入口跑不了。处置是能力探测 + 说明
  原因,**不摆按不动的按钮**。

### Android:编译成 `.so` 之后,"绿"最容易骗人的地方

`-PpadpdCompiled=true` 让 `src/padpd` 以 Android `.so` 进包(完整说明在
`android/README.md`)。这条路上每一个失败都长成同一副样子:**做对和做错的
构建日志一模一样**,只有专门去查的东西能分开它们。

- **`.py` 和 `.so` 并存 = 没编译**:app payload 在 sys.path 上排在
  requirements 前面,`.py` 会挡住 `.so`,APP 行为完全正常、体积还更大。
  所以 `compiled` 为真时 `stagePythonSources` 不再 staging `padpd/**`,
  这条互斥关系由 `tests/test_android_build_config.py` 用括号配对守着,
  设备测试跑完后再用 `inspect_apk.py` 查一次真正装上去的那个 APK。
- **两个 APK 只差一个名字**:同一 workspace 里前后构建,第二次复用第一次的
  pip 产物是最现实的失败。两次之间 `clean`,两个产物分别用
  `--native` / `--pure` 断言。这和之前那次"抽屉 APK 冒充 classic 上传"是
  同一个教训的第二次:**没有任何东西检查一个 APK 里装的是什么。**
- **一个 APK 得能被问出"你是谁"**:壳(2) × padpd(2) = 四个 release,Gradle
  把它们全叫 `app-release.apk`。每个包里现在有 `assets/padpd-build.json`
  记着构建时的两个选择,`scripts/android/apk_build_stamp.py` 把它变成断言,
  构建 job 与四条设备腿都查。**不能用 `BuildConfig` 字段代替**——两套壳的
  代码都编进两个 APK,classic 构建的 DEX 里照样有 `"drawer"` 这个字符串。
  设备腿也必须查:一条叫 `drawer` 的腿若构建的是经典壳,41 条测试会全过,
  因为它们本来就写成两套壳都成立。
  **生成的资源目录要交给 AGP 接线,不要自己按任务名挂 `dependsOn`。**
  第一版把目录加进 `sourceSets` 再钩住所有名字含 `assets` 的任务,
  release 构建直接失败:`lintVitalAnalyzeRelease` 也读 assets 目录,
  名字里却没有 `assets`。消费方的清单只有 AGP 知道,按名字匹配是打地鼠。
  正确写法是 `variant.sources.assets.addGeneratedSourceDirectory(task, …)`,
  输出目录也由 AGP 指定,任务自己不要设。
  (顺带一个有用的观察:同一轮里**设备腿是绿的**——`connectedDebugAndroidTest`
  不跑 lintVital,所以"资源确实进包、断言确实成立"那半当时就已经验到了。)
- **wheel 必须按 tag 装,不能按路径装**:`--find-links` + `install "padpd"`。
  给路径 pip 不做 ABI 匹配,arm64 的轮子会装进 x86_64 构建里,装得干干净净,
  在 import 时以一句 ELF header 错误炸掉,而那句错误指向的地方跟这里毫无关系。
- **`--compile all` 是断言不是开关**:它声称"把这些 `.py` 删掉测试仍全过"。
  证明办法是同环境里跑两遍桌面套件比计数(`android-compiled.yml` 的 `suite`
  job),不是拿另一个 job 记住的数字来比——通过/跳过的分布随装了哪些可选依赖
  而变。实测:453 passed / 17 skipped 两边一致。
- **唯一那条不一致的测试值得单独说**:`test_api_pages_reference_real_modules`
  断言 `docs/api/*.md` 里每个 `::: padpd.x` 都能找到 `.py` 文件。源码被
  故意删掉的树里它必然失败,而这跟 padpd 还能不能用无关。处置是**两遍都
  deselect**(不是只在编译那遍),理由写在 workflow 里。
- **反着验一次**:同一句 grep 必须在普通 `.pyc` 里**找得到** docstring、
  在 `.so` 里找不到。缺了前半句,写错的 grep 对两边都报"没找到",否定结论
  什么都不证明。
- **图表 fixture 的 spec 里也有浮点**:守卫最初声称"spec 是契约,不受舍入
  影响",按字节比。实测那句话是错的——`-53.87857429060689`(本机)对
  `-53.87857429072575`(runner),第 12 位有效数字之差,**五个平台连红三个
  提交而本地一直绿**。处置是两侧都过 `_round_floats`(7 位有效数字,比观测
  噪声多五个数量级),blob 那半早就是容差比的,漏的是 spec 这半。
  教训不是"加容差",是**"本地全绿"从来不是跨机器可复现的证据**。
  修完 spec 那半后,`android-deps-floor`(钉 numpy 1.23.3/scipy 1.8.1)又露出
  第二半:**blob 也变**,float32 低位尾数,实测相对差 7.9e-7。JSON 那条测试
  对 blob 早有容差,Kotlin 那条是整串按字节比、blob 一起比了。处置是把 Kotlin
  那条的契约拆成**骨架逐字符 + 数字按容差**,并把 round-trip 改成解**已提交
  的文件**(Kotlin 编译器读的是那个,不是刚生成的文本)。
  两半我都先判断过"这半未观测,不去过度设计"——**第二半在下一次 CI 就观测到了**。
- **Windows runner 的默认编码是 cp1252**:`read_text()` 不写 encoding,在
  Linux/macOS 上是 UTF-8、在 Windows 上是 cp1252,而 cp1252 没有 0x8f/0x90
  的映射——UTF-8 中文里这两个字节遍地都是。症状是
  `UnicodeDecodeError: 'charmap' codec can't decode byte 0x8f`,只在一个平台出现。
  **写测试的那台机器就是测试能过的那台机器**,本地永远发现不了。
  `tests/` 内一律要求写 encoding(不设"只在含非 ASCII 时"的例外——内容会变,
  调用不会),守卫见 `tests/test_docs_site.py`。
- **要说清它没买到什么**:字面常量编译后仍在常量池里,精确搜索就命中;
  没编译的 `gui_core/`、`padpd_mobile/`、`manual/`、`examples/` 仍是明文
  (`gui_core` 把 `manual/`、`examples/` 解析成自己目录的兄弟,搬进 wheel 就
  得连数据一起搬);界面上显示的数值不受任何影响。CI 里把"gui_core 没被
  编译"也写成断言,免得"编译版"被读成"里面什么都看不见"。

### 建模:相位谐波互不可表示

e^{+jφ}(主)、e^{−jφ}(镜像)、e^{−j3φ}(C-IM3)三类相位谐波在结构上
**互相表示不了**,各需专用分支。加新损伤前先判断它属于哪一类;若发生在
PA 之前,大概率存在精确代数预逆(参考 QMC),不必挤进 DPD 基。

## 教训

- **本地通过 ≠ 环境无关**:ONNX 与 streamlit 两个缺陷都是"开发机恰好装了
  某个包 / 版本恰好旧"造成的假绿。判断"这是我的改动还是环境差异"时,先比
  两侧的依赖与版本,再改代码。
- **负结果照写**:C-IM3 六种方案的失败、结构天花板的证明过程,写进
  docstring 与 CHANGELOG 后,直接省掉了别人重走弯路的成本。宁可写"这条路
  不通,因为 X",不要悄悄删。
- **诊断顺序**:遇到"应该能行但不行"的现象,先隔离变量(换 DUT、关损伤、
  缩短信号)再猜原因。测试死锁的三层根因、去嵌器的排序 bug、迟滞比 0.47
  都是靠逐项隔离找出来的,不是靠读代码想出来的。

## 开放问题

- 迟滞比在长观测窗下仍有约 2 倍的估计器偏差(线性 RC 的 DUT 读 0.51),
  目前的处置是**标注不可靠而非修正**。是否改用加热/冷却共享 τ 的联合拟合
  尚未验证——见 `docs/03_roadmap.md` 候选改进。
